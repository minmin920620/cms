Crime Mapping and Management System

1. Requirements Analysis: Current Technical Situation

The current technical situation of the organization involves the need for a centralized web-based system that can record, manage, monitor, map, and analyze crime incident data. Traditional crime recording often depends on paper forms, separate files, manual encoding, and delayed consolidation of reports. This causes difficulty in searching case records, tracking the progress of a case, monitoring barangay-level crime patterns, and preparing reports needed by administrators, police personnel, investigators, and local government users.

The developed Crime Mapping and Management System addresses this situation through a Laravel-based application with role-based access for Administrator, Police Officer, Investigator, and LGU users. The system supports authentication, dashboard summaries, crime incident management, evidence uploads, workflow status tracking, approval, notifications, mapping, hotspot viewing, analytics, report generation, user management, audit logs, and database backup. It uses a normalized relational database to store users, crime incidents, crime types, offense types, barangays, evidence, status history, assignment history, system notifications, and audit logs.

The system is designed for Koronadal City crime monitoring. Barangay data and map boundaries are used to support location-based visualization. Crime records include case number, title, crime type, offense type, barangay, report date and time, occurrence date and time, stage of felony, address, coordinates, reporter, assigned officer, status, investigation findings, approval information, and resolution data. This improves data retrieval, accountability, and decision-making compared with disconnected manual records.

Identified Problems

  • Manual or scattered crime records are difficult to search, update, and consolidate.
  • Crime status monitoring is delayed when case progress is not tracked in one workflow.
  • Crime location analysis is limited without map plotting and barangay-based summaries.
  • Evidence and supporting files can be separated from the case record.
  • Report preparation takes time when data must be manually filtered and counted.
  • User activity accountability is weak without audit logs and role restrictions.

System Objectives

  • To provide a centralized database for crime incidents, users, barangays, crime types, offense types, and evidence.
  • To support role-based access for administrators, police officers, investigators, and LGU users.
  • To allow authorized personnel to record, update, and monitor crime incidents.
  • To track case workflow from report received up to resolved or closed status.
  • To map crime incidents and identify barangay-level hotspots.
  • To generate analytics and reports for administrative and LGU decision-making.

3. Design of Software, Systems, Product, and Process

3.1 Conceptual Framework

The conceptual framework follows the Input-Process-Output model. Inputs include crime incident details, user account data, barangay and location data, crime type and offense type records, evidence files, status updates, approval data, and report filters. Processes include validation, authentication, role checking, case number generation, record storage, evidence management, mapping, analytics computation, report generation, notification handling, and audit logging. Outputs include crime records, status history, mapped incidents, hotspot summaries, analytics charts, printable reports, PDF exports, notifications, and audit records.

Figure 1. Conceptual Framework of the Crime Mapping and Management System

3.2 System Architecture

The system uses a web application architecture. Users access the application through a browser. Laravel routes receive requests and forward them to controllers. Controllers validate requests, apply role restrictions, call Eloquent models, and return Blade views or data responses. The database stores normalized records for users, crime incidents, barangays, crime types, offense types, evidence, histories, notifications, and audit logs. The storage layer keeps uploaded evidence files. Map and analytics interfaces display database results for monitoring and decision-making.

3.3 Use Case Diagram

The main actors are Administrator, Police Officer, Investigator, and LGU user. The Administrator manages users, crime types, offense types, reports, audit logs, backups, approvals, and crime records. The Police Officer records incidents, plots incidents, updates records, uploads evidence, views map data, and receives notifications. The Investigator reviews assigned cases, updates status, records findings, manages evidence, and monitors case progress. The LGU user views analytics and summary reports for planning and decision support.

3.4 Activity Diagram

The general activity starts when a user logs in. The system validates credentials and checks the user's role. After successful authentication, the system displays the role-based dashboard. Authorized users may create or update crime records, upload evidence, update status, view maps, generate reports, or view analytics. Each transaction is validated before being saved. Important activities may create notifications, status history, assignment history, and audit log entries. The activity ends when the user finishes the task and logs out.

4. Normalization

Normalization is applied to organize the system database and reduce redundancy. The system separates repeated data such as users, barangays, crime types, offense types, evidence files, status histories, assignment histories, notifications, and audit logs into related tables.

4.1 Unnormalized Form

In unnormalized form, one crime report may contain all details in a single wide record, including repeated evidence files, repeated officer data, repeated barangay data, repeated crime type names, and repeated status notes.

Case No.Incident DetailsCrime/OffenseLocationPeopleEvidence GroupStatus and Audit Data
CRM-20260816-0001Theft incident; reported and occurred dates; address; stage of felonyTheft; THEFT - RPC Art. 308Barangay name, city, latitude, longitudeReporter name, officer name, investigator nameEvidence file 1, evidence file 2, IRF, blotter copy, UCPER filePending, review notes, approval notes, old values, new values

This form causes duplication because barangay, crime type, offense type, user, and evidence information may be repeated for every incident.

4.2 First Normal Form

In First Normal Form, repeating groups are removed and each field contains atomic values. Evidence files are separated from the main crime incident record. Each crime incident has one value per field, while multiple evidence files are stored as separate evidence records.

TableSample FieldsPurpose
crime_incidentscase_number, title, date_reported, time_reported, date_occurred, time_occurred, address, latitude, longitude, statusStores one record per incident.
evidencecrime_id, file_path, file_type, file_name, category, description, uploaded_byStores one record per uploaded file.

4.3 Second Normal Form

In Second Normal Form, partial dependencies are removed by separating reference data into their own tables. Crime type, offense type, barangay, and user details are not repeatedly stored as plain text inside every incident record. Instead, the incident record stores foreign keys.

TablePrimary DataRelationship
usersname, email, password, role, phone, badge_number, avatar, is_activeLinked as reporter, assigned officer, uploader, approver, or notification recipient.
crime_typesname, description, icon, color, is_activeOne crime type can be used by many crime incidents.
offense_typesname, crime_type_id, description, is_activeOne offense type can be used by many crime incidents and may belong to a crime type.
barangaysname, city, latitude, longitude, is_activeOne barangay can be linked to many crime incidents.
crime_incidentscrime_type_id, offense_type_id, barangay_id, reported_by, assigned_officerUses foreign keys instead of repeated descriptive data.

4.4 Third Normal Form

In Third Normal Form, transitive dependencies are removed. Workflow history, assignment history, notifications, and audit details are stored in their own tables because they describe events related to a crime, user, or system action rather than being direct attributes of the main crime incident.

TableKey FieldsReason for Separation
crime_status_historiescrime_id, old_status, new_status, notes, changed_byStores multiple status changes per crime incident.
case_assignment_historiescrime_id, assigned_from, assigned_to, assigned_by, notesStores changes in case assignment over time.
system_notificationsuser_id, crime_id, title, message, type, read_atStores notification records separately from users and crimes.
audit_logsuser_id, action, auditable_type, auditable_id, old_values, new_values, ip_address, user_agentStores accountability records for system actions.
password_reset_otpsemail, otp, expires_at, used_atStores password recovery data separately from users.
