Corrected Normalization Section
Crime Mapping and Management System

Database Normalization

Database normalization was applied to the Crime Mapping and Management System to reduce data redundancy, avoid update anomalies, and maintain accurate relationships among crime incidents, users, barangays, crime classifications, offense types, evidence, status records, assignment records, notifications, and audit logs. The final database design separates repeated and dependent data into related tables using primary keys and foreign keys.

Unnormalized Form (UNF)

In the unnormalized form, all information about a crime incident may be stored in one wide record. This includes the crime details, barangay details, crime type, offense information, reporter and officer information, multiple evidence files, multiple status updates, notifications, and audit details. This design creates repeated groups and duplicated values.

The UNF structure is not ideal because evidence files, status changes, assignment changes, user details, barangay details, and audit data may repeat in a single crime record.

First Normal Form (1NF)

First Normal Form requires that each field must contain only one value and that repeating groups must be removed. In the system, multiple evidence files and multiple status updates are separated from the main crime incident record. Each evidence file becomes one row in the evidence table, and each status update becomes one row in the crime status history table.

Second Normal Form (2NF)

Second Normal Form requires that non-key attributes depend on the whole primary key and that data belonging to separate entities must be placed in separate tables. The system removes repeated descriptive data from crime records by separating users, crime types, offense types, and barangays into their own tables. The main crime record stores foreign keys instead of repeating names and details.

Separated EntityPrimary KeyFieldsRelationship to Crime Incident

barangaysidname, city, latitude, longitude, is_activeReferenced by crime_incidents.barangay_id.

After 2NF, the crime incident table no longer needs to repeatedly store the full crime type name, offense name, barangay details, or user account details. Those values are retrieved through related tables.

Third Normal Form (3NF)

Third Normal Form requires removing transitive dependencies. Data that describes events, logs, notifications, assignments, approvals, or password recovery should not be stored as repeated columns in the main crime incident or users table. The system separates these supporting records into dedicated tables.

Final Normalized Database Tables

Normalization Summary

Normal FormRule AppliedApplication in the System
UNFAll data may be stored in one wide record with repeating groups.Crime details, evidence files, status updates, barangay details, user details, notifications, and audit values are mixed together.
1NFRemove repeating groups and keep atomic values.Evidence and status histories are separated from the main crime incident record.
2NFRemove partial dependencies and separate entity data.Users, crime types, offense types, and barangays are stored in separate tables and referenced by IDs.
3NFRemove transitive dependencies and event-based data from main records.Assignment histories, notifications, audit logs, and password reset OTPs are stored in separate supporting tables.
