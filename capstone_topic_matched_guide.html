Use This One-Paragraph Current Technical Situation

The current technical situation of crime monitoring and record management requires a centralized system because crime incidents, evidence, case status updates, and reports can become difficult to manage when handled through manual forms, separate files, or disconnected records. The Crime Mapping and Management System is developed to support administrators, police officers, investigators, and LGU users in recording crime incidents, assigning officers, uploading evidence, monitoring case status, plotting incidents on a map, identifying hotspots, generating analytics, and preparing reports. Through a Laravel-based web application with role-based access, normalized database tables, audit logs, notifications, and barangay-based mapping, the system improves accuracy, retrieval, accountability, and decision-making for crime management in Koronadal City.

3.2 System Architecture

Lesson format: Provide a three-tier architecture figure and discuss it in one paragraph.

LayerFor Your System
Presentation LayerBrowser pages such as login, dashboard, crime records, map, analytics, reports, users, notifications, and audit logs.
Application or Business Logic LayerLaravel routes, middleware, controllers, models, validation, role checking, workflow rules, analytics logic, and report generation.
Data LayerDatabase tables, uploaded evidence storage, barangay GeoJSON data, sessions, cache, and backup files.

The three-tier architecture of the Crime Mapping and Management System separates the user interface, system processing, and data storage. The presentation layer allows users to access pages through a browser. The application or business logic layer handles authentication, role restrictions, validation, crime workflow, mapping, analytics, reports, and notifications through Laravel. The data layer stores users, crime incidents, crime types, offense types, barangays, evidence, histories, audit logs, notifications, and system files.

1NF

Apply 1NF by making each field atomic and removing repeating groups. Evidence records and status updates should not be stored as repeated columns in one crime record.

TableFields
crime_incidentscase_number, title, crime_type_id, offense_type_id, barangay_id, dates, times, address, coordinates, status, reporter, assigned_officer
evidencecrime_id, file_path, file_type, file_name, category, description, uploaded_by
crime_status_historiescrime_id, old_status, new_status, notes, changed_by

2NF

Apply 2NF by separating data that depends on separate entities. Crime type names, offense names, barangay information, and user information should be stored in their own tables and referenced using IDs.

Separated TableReason
usersStores user details once and links them as reporter, assigned officer, uploader, approver, or notification recipient.
crime_typesStores crime classification data once.
offense_typesStores legal offense categories once and can link to crime types.
barangaysStores barangay name, city, and coordinates once.

3NF

Apply 3NF by removing transitive and event-based dependencies. Logs, notifications, assignment histories, status histories, and OTP recovery records should be placed in separate tables because they describe events or supporting records connected to users and crimes.

Final Supporting TablePurpose
case_assignment_historiesTracks changes in assigned officers or investigators.
system_notificationsStores user notifications and read status.
audit_logsStores user actions, old values, new values, IP address, and user agent.
password_reset_otpsStores OTP-based password reset data.
