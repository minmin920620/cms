Chapter IV: Methodology, Results, and Discussion

Activity Diagram and Module Separation

The Crime Mapping and Management System is separated into thirteen modules based on the actual routes, controllers, models, and workflows found in the Laravel system. Each module below identifies its actors, major functions, and activity flow. The system actors are Administrator, Police Officer, Investigator, and LGU user.

1. Login and Authentication Module

ActorsFunctionsSystem Basis
Administrator, Police Officer, Investigator, LGULogin, logout, password reset through OTP, session authentication.Laravel Breeze authentication routes, password reset OTP mail, users table, sessions table.
  1. The user opens the login page.
  2. The user enters email and password.
  3. The system validates the credentials and active account status.
  4. If valid, the system opens the role-based dashboard.
  5. If invalid, the system displays an error message.

2. Dashboard Module

ActorsFunctionsSystem Basis
Administrator, Police Officer, Investigator, LGUView summary counts, recent cases, dashboard API data, and role-based overview.DashboardController, /dashboard, /dashboard/api-data.
  1. The authenticated user opens the dashboard.
  2. The system checks the user's role.
  3. The system retrieves counts and records appropriate to that role.
  4. The dashboard displays the current summary information.

3. Crime Incident Management Module

ActorsFunctionsSystem Basis
Administrator, Police Officer, InvestigatorView, create, update, soft-delete, filter, and manage crime records.CrimeController, crimes resource routes, crimes table.
  1. The authorized user opens Crime Records.
  2. The system checks role permission.
  3. The user adds, views, edits, or deletes a crime incident.
  4. The system validates title, type, offense type, barangay, date, location, status, reporter, and assigned officer data.
  5. The system saves the record, assigns or preserves the case number, and writes timestamps/audit details.

4. Crime Status Workflow Management Module

ActorsFunctionsSystem Basis
Administrator, Police Officer, InvestigatorUpdate case status from pending through the detailed investigative workflow up to resolved or closed.CrimeController updateStatus, expanded crime status migration.
  1. The user opens a crime record.
  2. The user selects a new status.
  3. The system checks whether the transition and role are allowed.
  4. The system stores status notes, investigation findings when applicable, findings recorded date, and resolved date when needed.
  5. The system shows a success or validation message.

The final status values are pending, ciras_recording, for_review, for_correction, data_stored, irf_printed, for_signature, blotter_entered, ucper_compiled, resolved, and closed.

5. Evidence Management Module

ActorsFunctionsSystem Basis
Administrator, Police Officer, InvestigatorUpload, view, and delete evidence files connected to a crime record.EvidenceController, evidence table, storage disk migration.
  1. The authorized user opens a crime record.
  2. The user uploads or views evidence.
  3. The system validates the file and linked crime record.
  4. The system stores file path, file name, file type, description, uploader, and storage disk.
  5. The system allows deletion only to authorized users and keeps the record soft-delete capable.

6. Crime Map Module

ActorsFunctionsSystem Basis
Administrator, Police Officer, InvestigatorView mapped incidents, retrieve map data, detect barangay, and plot an incident from the map interface.CrimeMapController, /map routes, barangay boundaries GeoJSON.
  1. The user opens the map page.
  2. The system loads crime locations and barangay boundaries.
  3. The user filters or selects a location.
  4. The system displays markers, coordinates, and barangay information.
  5. For authorized police/admin users, the selected map location can be used for plotting an incident.

7. Hotspot Module

ActorsFunctionsSystem Basis
Administrator, Police Officer, InvestigatorView high-incident areas and hotspot summaries.HotspotController, crimes and barangays data.
  1. The user opens the Hotspots module.
  2. The system retrieves crime records grouped by barangay/location.
  3. The system identifies areas with higher incident concentration.
  4. The user reviews hotspot results for monitoring and planning.

8. Analytics Module

ActorsFunctionsSystem Basis
Administrator, LGUView trends, crime by type, crime by barangay, status breakdown, and monthly report data.AnalyticsController, analytics route group restricted to admin and LGU.
  1. The user opens Analytics.
  2. The system confirms Admin or LGU role.
  3. The user selects an analytics view.
  4. The system retrieves crime data and generates charts/statistics.
  5. The user reviews the results.

9. Report Management Module

ActorsFunctionsSystem Basis
AdministratorGenerate, preview, print, and export filtered crime reports.ReportController, reports routes, export-pdf route.
  1. The administrator opens Reports.
  2. The system displays filter options.
  3. The administrator selects crime type, barangay, status, and date range.
  4. The system retrieves matching crime records.
  5. The system shows report preview and allows print/PDF export.

10. User Management Module

ActorsFunctionsSystem Basis
AdministratorCreate, view, update, deactivate, and delete user accounts.UserController, users resource routes, users table.
  1. The administrator opens User Management.
  2. The system displays accounts.
  3. The administrator creates or edits name, email, role, phone, badge number, avatar, and active status.
  4. The system validates uniqueness and role values.
  5. The system saves the account changes.

11. Crime Type Management Module

ActorsFunctionsSystem Basis
AdministratorCreate, update, deactivate, or delete crime classifications.CrimeTypeController, crime_types table.
  1. The administrator opens Crime Types.
  2. The system displays existing crime types.
  3. The administrator enters name, description, icon, color, and active status.
  4. The system validates and saves the crime type.
  5. The system prevents unsafe deletion when referenced by records.

12. Offense Type Management Module

ActorsFunctionsSystem Basis
AdministratorCreate, update, deactivate, or delete offense types linked optionally to crime types.OffenseTypeController, offense_types table, normalized offense migration.
  1. The administrator opens Offense Types.
  2. The system displays offense type records.
  3. The administrator enters the offense name, optional linked crime type, description, and active status.
  4. The system validates unique offense names.
  5. The system saves the offense type and makes it available to crime records.

13. Audit Log and Account Profile Module

ActorsFunctionsSystem Basis
Administrator for audit logs; all users for profileReview audit logs, update profile information, change password, and manage own account settings.AuditLogController, ProfileController, audit_logs table, profile routes.
  1. The administrator opens Audit Logs to review user actions, affected records, old values, new values, IP address, and user agent.
  2. Any authenticated user can open Profile Settings.
  3. The user updates profile information or password.
  4. The system validates the submitted data and saves changes.

Database Normalization

The normalization below is based on the actual system entities: users, crimes, crime types, offense types, barangays, evidence, audit logs, sessions, password reset tokens, and password reset OTPs. The purpose is to show how a single unorganized crime-report record becomes the current relational database design.

Unnormalized Form (UNF)

In UNF, one crime report stores all information in one wide record. Repeating evidence files, repeated officer/investigator details, repeated type names, and repeated barangay data are mixed with the crime incident details.

Case No.Incident DetailsCrime/OffenseBarangay/LocationPeopleEvidence GroupStatus/Audit
CRM-20260806-0001Title, date reported, time reported, date occurred, time occurred, stage of felony, status notes, investigation findingsCrime type name, description, icon, color; offense name and descriptionBarangay name, city, latitude, longitude, address, street/highwayReporter name/email/role/badge; assigned officer name/email/role/badge; uploader name/emailEvidence 1 file name/path/type/description; Evidence 2 file name/path/type/description; more evidence columns if neededStatus, resolved date, action, old values, new values, IP address, user agent

Problem: one case may have many evidence files and many audit actions. Storing them in the same row creates repeating groups, duplicated names, update anomalies, and difficulty filtering reports.

First Normal Form (1NF)

In 1NF, repeating groups are removed. Each evidence item and each audit action is placed in its own row. However, descriptive data such as user names, crime type names, offense names, and barangay names can still repeat in many rows.

1NF TableAtomic FieldsRemaining Issue

crime_evidence_rowscase_number, file_path, file_type, file_name, description, uploaded_by_emailUploader and case details can repeat for each evidence item.
crime_audit_rowscase_number, user_email, action, old_values, new_values, ip_address, user_agent, created_atUser and auditable record details can repeat for each audit entry.

Second Normal Form (2NF)

In 2NF, data that depends only on one subject is separated into its own table. Crime records keep foreign keys instead of repeating full names and descriptions. Evidence depends on a crime, audit logs depend on a user and an audited record, and reference data is separated.

Third Normal Form (3NF)

In 3NF, non-key attributes depend only on the key of their own table. The final design removes transitive dependencies: offense data depends on offense_types.id, barangay data depends on barangays.id, user profile data depends on users.id, and evidence metadata depends on evidence.id.

The final 3NF structure supports the thirteen modules by keeping operational records, reference data, authentication data, evidence files, and audit history in separate but related tables. This reduces duplication, improves report accuracy, and protects data integrity through primary keys, unique fields, foreign keys, indexes, role-based access, and soft deletes where required.
